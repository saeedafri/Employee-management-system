## 1. Confirmed defects in EMS (severity order)
Legend: [E2E] reproduced live locally · [SRC] confirmed by code reading with file:line · [UNV] reported, not reproduced.

## 3. Competitor internals — what the teardown showed
**Design ideas worth adopting (from OSS source):**
- Leave: Odoo seniority-tiered accrual plan levels; Frappe pre-computed earned-leave schedule (deterministic backfill/mid-year joiners); OrangeHRM FIFO entitlement lots (carry-forward expiry, correct restore on cancel); snapshot ledger per leave year.
- Payroll: Frappe dated `arrear`/`payroll_correction` applied in a later run (never edit old slips); `additional_salary`, `salary_withholding`, YTD opening balances, statistical-component flags; projected annual tax (YTD + remainder) with two-stage declaration/proof; unified Full & Final statement (assets, advances, loans, withheld pay, encashment).
- Rules as data: Horilla conditional allowances; Odoo work-entry/time rules → OT, night, holiday premium.
- Attendance: Frappe auto-attendance with sync cursor + shift rotas; Horilla biometric connectors (Anviz, COSEC, Dahua, eTimeOffice).
- Platform: generic approval-workflow engine + delegation (Jorani); editable i18n strings (OrangeHRM); custom fields; webhook/automation tables.
**Pitfalls to avoid:** god classes (Frappe salary_slip.py 2.8k lines, Odoo hr_leave 2.7k); evaluating stored formulas (Horilla had RCE via `exec`; Frappe's sandbox is a denylist). EMS's `src/utils/formulaEval.js` uses a strict uppercase-only regex + `new Function`; not exploitable as written (see §0), but replace with an AST allowlist parser (jsep/expr-eval) as hygiene. Unbounded ledger sums on read; full-year tax recompute per slip; soft-delete states complicating reversal.
**Public API conventions to match:** API keys + OAuth client-credentials with ~90 resource:read/write scopes (Remote); cursor pagination + `updated_since` change feeds (BambooHR/Factorial/Rippling); dated API-version header (Gusto/Rippling); Idempotency-Key + optimistic version (Gusto); structured errors (`error_key`, category, metadata); X-RateLimit headers; signed webhooks (HMAC-SHA256 + timestamp), retries (Factorial 20x/48h), delivery log, replay, ~92-137 event types (EMS: 12 names in a Setting JSON, no dispatch); async bulk + sandbox simulator. Entities EMS lacks: custom fields/objects, effective-dated job & comp history, dependents/emergency contacts, job catalog/pay grades/bands, cost centers/teams/locations, shifts/overtime, blocked leave periods, benefits plans, onboarding tasks/probation, comp planning, recurring incentives, company-file categories, Form 16 real.
**Frontend/architecture (REA, observed):** Keka (ASP.NET MVC+jQuery, 138KB gz login), Zoho (jQuery login 134KB gz; passkey/WebAuthn, TOTP, SAML, social — richest auth), HiBob (Angular, 620KB login, Descope), Rippling (React/webpack, 2.4MB gz at login, own design system), Factorial (Rails+Vite, ~24MB transfer — heaviest), Deel (React/Vite, only PWA manifest). No micro-frontends, no service workers, no public source maps anywhere; Arabic/RTL weak except Jisr/ZenHR. EMS FE: 6.2MB static, no dynamic imports, client-side auth guard, no i18n — a lean login (<300KB gz), per-module splitting and server-side auth is an easy win over most.
